# 微信控件定位与游戏重开

微信首次启动、顶号恢复和白屏／黑屏／持续无响应恢复共用控件启动链路，已不再使用图片模板识别入口。抖音仍使用独立的图片导航；微信白屏／黑屏判断仍会截图。

## 定位方式

- 微信原生导航：`wechat_native_controls.js` 通过 Frida 只读微信主进程的 Qt 控件树，读取控件名称、实时矩形和父子关系。由窗口客户区尺寸换算 DPI 后，使用正常鼠标输入点击唯一目标。点击前重新检查前台窗口、位置、尺寸和遮挡。
- 不按微信版本号选择布局，也不保存固定模块偏移表。通过 `mmui::MainWindow` 的 Qt 字符串元数据、元对象、机器码引用和虚表引用自动反推位置，随后校验 QObject 归属、实际窗口所属 PID、几何与 DPI。已经打开最近使用页面时可直接使用文本入口，无需原生探测。当前对象结构读取面向 Windows x64／现有 Qt 结构；框架大幅变更导致结构验证失败时停止点击，并记录结构错误。
- 最近使用：`wechat_recent.ps1` 通过 UI Automation 找到“小程序”文档中“最近使用”下的唯一普通版“遗弃之地”。排除“我的常用／我的小程序”以及开发版、体验版。同名候选不唯一时停止。
- 原生探测在插件的工作线程中执行：同一微信PID和进程创建时间复用一个Frida会话、一个控件脚本，不为每个Snapshot／Click启动助手或重新注入。脚本／会话失效、进程变化时才重新挂载，插件退出时释放。检查游戏窗口及普通输入不注入Frida。扫描最多等待25秒，超时不取消在途RPC，收尾前不开始第二次扫描。JS只读Qt内存，不调用NativeFunction；窗口归属、矩形与DPI由外部读取并传入，Qt类名按已校验长度读取。

## 位置缓存与失败回退

首次扫描后，位置持久保存到用户配置目录的 `wechat_launch_positions.json`。缓存不含 Qt 对象地址；自动发现的虚表相对位置另按模块头指纹缓存，同一指纹复用时再次验证元数据，指纹变化或结构失效时自动重定位。原生控件保存相对客户区位置及微信进程身份，网页游戏入口额外保存 UIA RuntimeId。窗口平移后重算坐标；进程、尺寸、DPI 或控件身份变化时拒绝旧位置并重新扫描。

首次启动与游戏重开共用同一逻辑：优先验证并使用缓存位置，失效时在前台重新定位。前台查找原生控件和游戏入口时，直接保存本次得到的位置。不启动独立的后台位置刷新任务。前台刚扫描到控件后直接复用其位置，点击前验证进程、窗口尺寸、DPI和遮挡；验证失败才重新读取控件。已删除旧坐标校准按钮和传参链，旧配置中的wechat_sidebar字段读取时自动丢弃。

缓存点击后最多等待15秒确认游戏窗口。若没有打开，先确认游戏没有延迟出现，再前台重新定位、保存新位置并重试一次。初次点击已打开游戏但回执丢失时不重复点击；两次尝试均失败则结束本轮。缓存文件损坏或写入失败不影响正常扫描。

微信主进程优先按实际微信主窗口的 PID 识别，不因多个启动器／辅助进程而直接失败。没有主窗口时只接受唯一的非辅助候选；窗口仍有歧义时记录候选 PID。启动检查只有成功后才标记完成，未运行、更新中或定位失败时每20秒重新检查；已有游戏窗口会先被识别，不重复打开。

## 点击前预热

首次启动时，微信导航与小游戏调试监听并行准备；只有两者都成功才允许点击游戏入口。导航过程中预热一个 UIA 辅助进程，后续导航和最终校验复用它，避免每一步重新加载 PowerShell／UIAutomation。位置缓存随前台查找结果更新，后台不扫描控件或游戏入口。

准备阶段返回本轮入口信息，启动和重开直接复用；最终点击仍按 RuntimeId、窗口位置和现有游戏窗口做即时核对。重开时先验证入口、关闭旧游戏，再准备监听，避免在旧游戏仍运行时重置其调试连接。移除无条件等待，仅在恢复最小化窗口或切换前台时作短暂等待。

预热进程空闲时阻塞等待命令，不做循环扫描；每条命令有超时，通信失败时回收进程且不重放点击，退出插件时关闭它。

## 触发条件

- 顶号：沿用顶号设置和等待时间，只处理游戏原生账号重复登录事件。
- 白屏／黑屏：游戏客户区持续纯色至少15秒，且连续确认3次。
- 持续无响应：对已有游戏上下文的独立轻量探测持续失败60秒，且至少确认3次。一次成功会清空确认计时；截图失败不会阻断此分支。
- 用户关闭自动恢复、退出插件、已确认顶号时不运行该恢复分支。每轮结束冷却5分钟。单次任务弹窗失败不会直接被视为游戏无响应。

## 流程

1. 预检查并导航到最近使用页面，验证唯一游戏入口；失败时保留当前游戏窗口。
2. 只向唯一的目标游戏窗口发送普通关闭消息，等待最多15秒；未关闭则停止，不杀微信进程。
3. 调用原有 prepare_reopen，先准备小游戏 Frida 调试监听。
4. 重新确认最近使用入口，并检查是否已有游戏窗口，防止重复打开。
5. 优先按缓存位置点击游戏入口；未确认打开时，使用新扫描位置重试一次，每次点击前重新检查游戏窗口。
6. 由原有连接流程确认大厅并挂载功能。
7. 挂载后处理开屏活动队列：抖音0.1.73的活动模块确认使用 `StitchSoulFirstFaceUI`，仅点击绑定到页面 `close` 的按钮。等待队列清空和大厅稳定2秒才交给功能初始化；陌生页面或未核实按钮停下等待人工处理。

断线截图写入 `logs/recovery/blank_white.png` 或 `blank_black.png`，每种仅保留最近一张。
控件点击要求微信窗口可置前，目标未被其他窗口遮挡。窗口移动、尺寸变化、候选不唯一或对象结构校验失败时停止并记录阶段。白屏／黑屏截图检查沿用原有可见窗口限制。

重启前在助手内存中标记正在运行的日常自动化、三尸合成和手动狗粮自动合成。只有确认已重新打开游戏，且新会话已关闭开屏页、完成功能初始化、旧任务已收尾后，才消费一次标记从头启动。日常处理器和调度时间重置，合成重新读取库存，不重放结果未知的命令。狗粮已包含在日常托管时不另外重复启动。用户点击停止会取消相应恢复标记；助手进程退出后不保留标记。


## 原生扫描崩溃诊断

`%LOCALAPPDATA%/e0e1/e0e1-wx-plugins/wechat_native_probe.log` 记录attach、脚本加载、元数据扫描、主窗口扫描、控件遍历和detach阶段，以及Frida脚本错误、会话脱离原因。日志超过1MiB后保留一份previous文件，不记录聊天内容。

2026-10-28的08:25、08:26崩溃转储显示，同一Weixin.exe中存在两个不同临时目录的frida-agent.dll，异常为0xc0000409，故障位于frida-agent内部。已取消缓存导航与后台原生扫描的并行注入，原生扫描串行执行。该证据不能单独证明具体哪条JS语句导致崩溃，后续需结合阶段日志和新的实机结果确认。启动重试在监听保留期内复用监听，避免20秒重试再次停止刚准备好的调试会话。


小游戏调试Hook挂载在独立的WeChatAppEx进程，与微信主进程控件会话分别保留。Hook仍有效时不因缺少CDP回连而反复卸载重装；会话脱离或脚本销毁时发布失效状态，再允许重建。新WMPF配置自动检测与正式Hook共用同一个Frida会话，检测脚本卸载后加载正式Hook，不重复attach。


发现页的小程序入口可能由`mmui::ExtensionDiscoverContentCell`直接保存文字，并不存在独立的`XTextView`子控件。原生扫描同时识别这种列表单元，在限定范围内读取“小程序”文字，再使用该单元的实际矩形点击；不能仅凭UIA文本匹配为零判断页面不存在或被安全机制拦截。
